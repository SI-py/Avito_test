# Гибридный поиск: эксперименты и выводы

## Как устроена проверка

Локальный holdout собран из обучающих строк, чьи `item_id` присутствуют в
`benchmark_items.parquet`: 3 200 уникальных полных контекстов запроса, по 1 600
на подбор и финальную проверку. Для поведенческих профилей использовались только
строки с объявлениями **вне** benchmark-корпуса. Поэтому релевантное объявление
не могло попасть в ответ через lookup-профиль.

Reranker обучался лишь на первой половине, а все итоговые числа ниже посчитаны
на второй. В признаках нет `item_id`: только ранги и cosine similarity каналов,
совместимость локации/микрокатегории и агрегированные признаки качества.

## Главные результаты

| Метод | Recall@50 на holdout |
|---|---:|
| Word TF-IDF, смешанное поле | 0.248 |
| Char TF-IDF | 0.230 |
| RRF: mixed + char | 0.254 |
| RRF + location transitions + microcategory + popularity | 0.386 |
| То же + exact-location quota 40 | 0.488 |
| Линейный reranker над полным union | **0.577** |
| Reranker + exact-location quota | **0.578** |
| Reranker + leakage-safe history RRF | **0.580** |
| Oracle по union пяти каналов | 0.614 |

Последняя строка — не настоящий top-50, а диагностический потолок: доля
релевантных объектов, найденных где-либо в полном union из пяти списков
top-180. Разрыв `0.614 - 0.580` показывает, что основной резерв теперь в
reranking, а не в резком расширении индекса.

## Что оказалось важным

1. **География — не просто равенство ID.** Выученный переход
   `search_location_id -> item_location_id` оказался сильнее бинарного exact
   match: `0.409` против `0.373` на tune. Это объясняет случаи поиска по городу с
   выбором объявления из области или соседней агломерации.
2. **Один монолитный текст лучше ручного fielded-RRF.** Отдельные поля полезны
   как источник широкого union, но простое объединение их рангов проиграло
   `mixed + char`. Вес полей лучше учить на кликах.
3. **Char-канал дополняет word-канал.** Он устойчив к опечаткам, окончаниям и
   слитному написанию; его reciprocal rank — один из сильнейших коэффициентов
   модели.
4. **Микрокатегория полезна как мягкий prior.** Точное соответствие истории и
   char-centroid помогают, но слабее географии и текстовых сигналов.
5. **Историю нельзя делать единственным источником.** Даже при совпавшем тексте
   запроса пользователь мог искать другой тип услуги. Мягкий RRF дал небольшой,
   но стабильный прирост; жёсткая вставка исторических объектов не нужна.

## Коэффициенты reranker

Самые сильные положительные признаки: вероятность перехода локации, char rank,
mixed cosine, char cosine и popularity. Отрицательные коэффициенты отдельных
полей (`params cosine`, raw rating) не следует читать причинно: признаки
коррелируют, а модель использует их совместно. Например, высокий рейтинг без
числа отзывов часто менее надёжен, чем их комбинация.

## Почему это похоже на production-поиск Авито

Открытые материалы Авито описывают каскад: широкий retrieval из инвертированного
и семантического поиска, затем несколько уровней ранжирования. Отдельно
используются понимание запроса, фильтры, география и поведенческие признаки.
Наше решение — компактная офлайн-версия той же идеи:

```text
5 lexical channels -> union до ~900 объектов -> linear reranker -> top-180
                    -> soft history RRF -> small location quota -> top-50
```

Подробный разбор источников находится в `avito_research.md`.

## Рекомендованный файл

относился к `answer.csv`, а не к v3.

## Ограничения

- Holdout сформирован из train и может быть легче скрытого benchmark.
- Положительные события не имеют времени, поэтому нельзя сделать настоящий
  temporal split.
- В обучающих данных видны только выбранные объявления, но нет показов; sampled
  negatives из retrieval union неизбежно содержат неизвестные положительные.
- Поэтому локальные `0.580` нельзя обещать на leaderboard; корректно ожидать
  направление улучшения, а не перенос числа один к одному.
